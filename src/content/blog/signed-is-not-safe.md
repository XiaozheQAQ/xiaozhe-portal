# 签名有效，不等于安全

11 月 26 日早上 9 点 56 分，安全软件弹了一条不太起眼的告警：`svchost.exe` 试图访问一个陌生域名。

`svchost` 是 Windows 自己的服务宿主，看到它的名字，大多数人的第一反应要么是"系统进程被感染了"，要么干脆关掉不看。我当时也差点划过去——直到我发现，同一时刻还有另一条日志，真正的发起者根本不是 `svchost`，而是 `steam.exe`。

这篇文章是对那天上午的一次完整复盘。它不是一篇"删掉这个文件就好了"的教程，而是一次判断过程：一条告警怎么被追到两个文件、一张证书、一家公司；以及这一路上，我差点被自己骗过去的几个地方。

![火绒安全日志：steam.exe 与 svchost.exe 访问仿冒域名已被拦截](/images/blog/signed-is-not-safe/huorong-alert.webp)

> [!NOTE]
> 文中所有恶意域名都已做去链接处理（`hxxp` + `[.]`），不会被误点；不会出现任何个人信息、样本文件或"入库工具"的操作方法。

## 一、那条告警，其实是个"跑腿的"

先说清楚为什么告警里会出现 `svchost.exe`。

Windows 上几乎所有程序要访问网络，第一步都得先把域名翻译成 IP 地址，这个动作叫 DNS 解析。而系统为了省事，让一个叫 **Dnscache**（DNS 客户端服务）的东西统一代劳——它本身就跑在 `svchost.exe` 里面。[^dnscache]

所以，当某个程序想连一个域名时，日志里"发起解析"的进程往往是 `svchost.exe`，真正想连网的程序躲在后面。我那两条告警里的 `svchost.exe`（PID 3648）经核查就只承载了 Dnscache 服务，是个替人跑腿的中间环节，不是元凶。

同一时刻的另一条日志，把真正的发起者写得很清楚：`steam.exe`。

> 一条 svchost 告警，可能只是 DNS 客户端在替别人跑腿。

这个认知很重要。如果我一看到 `svchost` 就往"系统被感染"的方向查，会绕很大一圈；反过来，如果看到 `svchost` 就当作正常系统行为忽略掉，就会漏掉真正的问题。判断的依据不是进程名字，而是同一时间窗口里"谁在请求、请求了什么"。

## 二、第一个发现：多出来的那个文件

顺着 `steam.exe` 往下查，我去核对了 Steam 客户端目录里每个可执行文件的数字签名。

Steam 自己有一套完整性清单（`steam.signatures`），官方文件都在里面。我把 Steam 目录下 77 个可执行文件挨个过了一遍签名，结果只有两个文件对不上——它们都不在 Valve 的清单里。

第一个，是 Steam 根目录下的 `xinput1_4.dll`，673,784 字节（约 658 KB）。

`xinput1_4.dll` 本来是 Windows 系统里一个和游戏手柄相关的组件，几乎是每个游戏玩家目录里都见过的名字。把恶意文件起成这个名字，放在 Steam 根目录，靠的是 Windows 加载 DLL 时"就近优先"的习惯——程序要找某个 DLL，会先看自己所在目录。[^dllorder] 于是 Steam 一启动，就把这个"同名"的文件当成了自家的组件加载进去。

这就是所谓 **DLL 搜索顺序劫持**：不修改 Steam 本身，只是放一个名字对得上的文件在旁边，让它被"顺手"加载。

## 三、签名是真的，可签名的人已经注销了

如果故事到这里结束，它只是一个普通的"放了个坏 DLL"。真正让我停下来的是它的签名。

这个文件有 **GlobalSign 的 EV 代码签名证书**，签名校验是"有效"的。[^ev] 换句话说，从系统角度看，它是一个"有身份、签发后没被篡改"的文件。

问题在于，签名只回答一个问题：**这个文件是谁签的、签完之后有没有被人改过。** 它从不回答另一个问题：**签这个名的，是不是个正经做软件的人。**

我去查了签名主体"NewWnight Global Tech Co., Ltd"。顺着证书里的工商注册号（91430103MADWKFRYXD）对回国内工商信息，它对应的是"长沙鑫夜科技有限公司"。这组数据摆在一起，很说明问题：

| 项目 | 情况 |
| --- | --- |
| 注册资本 | 5 万元 |
| 参保人数 | 0 人 |
| 成立时间 | 2024-08-28 |
| 当前状态 | 已注销 |
| 注册地址 | 集群注册（多家企业共用一个地址） |
| 工商变更 | 无 |
| 知识产权 / 行政许可 | 无 |

一家注册资本 5 万、零参保、集群注册、成立刚满一年就注销、没有任何经营沉淀的公司，却持有一张年费通常要几千元的 EV 代码签名证书。

> [!WARNING]
> 这里要非常克制：以上只是"特征高度吻合"，**不等于**已经证明存在证书买卖。我没有、也不打算下这个结论。但"为了拿到一张可信签名而临时设立的主体"这个画像，和眼前这组数据是能对上的。

更细的一层在文件的"版本信息"里。这个 DLL 把自己的公司名写成了 `Vale Corporation`——比 Valve 少了一个字母 v。产品名写成 `Vale`，文件描述写成 `Vale Dynamic Link Library`。

这不是手滑。它要骗的不是签名验证（签名和版本信息是两回事），而是扫一眼版本信息、看到"Valve 相关"就点"允许"的人。

> 那个 DLL 把公司名写成 Vale Corporation——比 Valve 少一个字母。它要骗的不是签名验证，而是扫一眼就点"允许"的人。

## 四、五天后追加的那个文件，才真正让人不安

第一个文件落地是 10 月 22 日深夜。它内部带着一段用 libcurl 写的下载逻辑，以及三个 `.../version` 形式的地址，本质上是一条"驻留 + 随时拉新东西"的通道。

真正让我后背发凉的，是 10 月 27 日晚上落地的第二个文件：`D:\steam\bin\Authorization.dll`，146,432 字节，**没有任何签名，也没有任何版本信息**。

它的名字 `Authorization`（授权）听起来很"正经"，仿佛是 Steam 授权体系的一部分。但它能干的事是这样的：

- 用 Windows 自带的 WinHTTP 库建立网络连接；
- 连上之后用 WebSocket 维持一条**长连接**；
- 第一包就上报：设备标识、主机名、操作系统版本、进程 ID。

它甚至有一个专门的导出函数叫 `GetAuthorizationHash`，以及一段写死的上线报文，大意是"你好，我是 token，我的设备是 X，主机名是 Y，系统是 Z，进程号是 N"。

说得直白一点：**第一个文件放进来的是"通道"，第五天放进来的是"眼睛"。**

到这里就能看出一个关键破绽。这个工具对外宣称的功能是"把游戏加进库"。可"入库"这件事，本质上是改本地的清单文件，**根本不需要**向外部服务器上报你的机器指纹，更不需要一条能接收指令的 WebSocket 长连接。

> `Authorization` 这个文件的能力，和它宣称的功能毫无关系。

两个文件的投放间隔整整五天，先后呼应，一个负责"进来并保持更新"，一个负责"回传并等待指令"——这已经不是"工具夹带了点私货"能解释的了。

## 五、溯源：一条编译路径出卖了它

恶意程序通常会把痕迹擦干净，但开发者有时候会忘记一件小事：编译时写进程序里的**调试符号路径（PDB）**。

第一个文件的 PDB 路径是：`I:\sTCode\x64\Release\update.pdb`。

这条路径信息量不小：`sT` 对应的是 SteamTools 这个工具，`update` 是模块名，而 `I:\` 说明它是在某个人自己的电脑的 I 盘上编译出来的。

本机还有几处旁证能对上：

- 存在 `D:\steam\config\stplug-in` 这个 SteamTools 专用的插件目录；
- 浏览器历史里有该工具官网、论坛的访问记录，以及"清单脚本"相关的搜索；
- 卸载注册表里没有任何相关条目——说明用的是绿色版，解压即用；
- 文件没有浏览器下载标记（Zone.Identifier），说明不是从浏览器直接下下来的。

这些线索拼起来，投放路径就指向了第三方"入库"工具这条生态。**这里只陈述线索，不提供任何获取或使用这类工具的方法。**

## 六、反转：同时报警的那个开源插件，其实是误报

就在处理这件事的同时，同一台机器上还弹了另一类告警，差点让我以为"还有第二个马"。

安全软件对一个开源浏览器插件 `dsh-doyourweb`（MIT 协议，GitHub 公开仓库）里的 `lib/host.js` 报了"下载者木马"，一共 8 条——后来发现只是同一个文件在运行目录和依赖缓存里被重复计数。

![火绒全盘查杀：dsh-doyourweb 被启发式误报为下载者木马](/images/blog/signed-is-not-safe/false-positive-scan.webp)

我去核验了一遍：把上游同一个 commit 的源码包下下来，逐个比对已提交的文件，30 个里 29 个哈希完全一致，剩下 1 个是打包工具本来就会排除的 `.npmignore`。**文件没被改过。**

那为什么会被判成木马？因为这段代码为了枚举窗口、读取图标、解压自带的扩展，用了 `-EncodedCommand` 加 base64 去调用系统命令，还用了 `ZipFile::ExtractToDirectory` 解压写盘。

而"base64 编码的系统命令 + 解压写盘"这个组合，恰恰是下载者木马最典型的行为形态。功能正当，但"长相"和真马重合了。

> [!TIP]
> 遇到 JS 类告警，先看三件事：有没有 `eval` / `new Function` 这种运行时拼代码的混淆；它连接的地址是不是只有本机和已知服务；能不能和开源上游逐字节对上。

还有第三类告警。清理完成之后，`WorkBuddy.exe` 又被报访问了那三个恶意域名。这一次的原因更"乌龙"：预览面板在渲染一段带超链接的 Markdown 时，Chromium 内核顺手对链接做了 DNS 预解析（提前把域名翻译成 IP，好让点击更快），并没有执行任何代码。

![火绒日志：WorkBuddy.exe 触发 DNS 预解析误报](/images/blog/signed-is-not-safe/dns-prefetch.webp)

判据也很简单：**看操作进程**。被注入的是 Steam，那么一旦复发，发起者必然是 Steam 相关的进程；如果弹出来的是文档查看器、浏览器、聊天客户端，先怀疑它是在解析你正文里出现的链接。

## 八、我没有查清的部分

一篇负责任的技术复盘，必须把"查不清"的地方也写出来。这几点是我这次没能确认的：

- **投放时具体运行了什么程序**：系统的预读取记录（Prefetch）被清空，最近使用记录、临时目录、回收站、崩溃报告里都没有残留。痕迹已经被清理工具抹掉了，无法锁定当时运行的 exe 和它的下载地址。
- **那几个域名的服务器归谁**：三个域名全部解析失败，没能观察到真正的通信内容。
- **有没有数据被传出去**：没有证据表明外传成功（域名都在联网前被拦下了），但在拦截生效之前是否有过短暂通信，我无法完全排除。
- **第二个文件是谁放进去的**：它没有签名、没有 PDB，无法确认是工具官方投放，还是第三方二次打包。

> 溯源的上限不是技术不够，是痕迹已经被清理软件抹掉了——这本身也是一条信息。

还有两件"具备能力、但未见使用"的事需要交代：系统受信任根里被发现装了两张第三方自签名 CA（其中一张带私钥、有效期写到 3025 年），但检索全部证书存储后确认，它们都没有签发过任何下级证书，也就是没发现实际被拿去做中间人攻击的痕迹。另外，Windows Defender 的实时保护此前被第三方安全软件接管关闭了，眼下机器只剩一道防线——这也是我接下来要处理的事。

## 九、后续：一封举报信，和一张被吊销的证书

写完复盘的同一天，我向签发这张证书的 CA（GlobalSign）提交了一份滥用举报，附上样本哈希、签名主体画像与调查结论。

![提交给 GlobalSign 的滥用举报邮件，个人信息已脱敏](/images/blog/signed-is-not-safe/abuse-report.webp)

当天就收到了受理回执，工单号 **09022095**。CA 的核验结论写得很直白：

> "We have investigated your claims and have confirmed that the malicious code was indeed signed with our Subscriber's certificate."

（我们已完成调查，确认恶意代码确实是使用我们客户的证书签署的。）

第二天早上 7 点 19 分（UTC），GlobalSign 的 CRL（证书吊销列表）[^crl] 刷新，序列号 `046CD9B4FAD9F7C7101A6578` 出现在了名单里。当天 18 点 18 分，我按在线模式重跑了一次证书链校验：链构建失败，状态是 **Revoked**——吊销正式生效，从提交举报到生效不到 24 小时。

### 软失败：证书吊销了，系统还说"签名有效"

这里面藏着一个更值得记下来的细节。证书明明已经进了吊销列表，我再对样本跑一次 `Get-AuthenticodeSignature`，它**依然返回 `Valid`**，"签名已通过验证"。

原因是 Authenticode 的默认校验对吊销采取**软失败（soft-fail）**策略：不强制在线查询，或者直接沿用本地缓存。换句话说，"签名有效"这个判定，默认情况下根本不会去核实证书有没有被吊销。想看到真实状态，必须显式做一次在线链校验：

```powershell
$sig   = Get-AuthenticodeSignature "sample.dll"          # 可能仍显示 Valid
$chain = New-Object System.Security.Cryptography.X509Certificates.X509Chain
$chain.ChainPolicy.RevocationMode = 'Online'
$chain.Build($sig.SignerCertificate)                     # False
$chain.ChainStatus                                       # Revoked
```

这把前面的结论又往前推了一层：签名不仅"必要不充分"，它给出的默认答案，本身就可能滞后于事实。

### 删文件救一台机器，吊销证书废一个生态

删掉本地两个 DLL，覆盖的是我这 1 台机器；而吊销这张证书，让这个主体签发的**全部**样本，在所有启用 CRL / OCSP 校验的环境里同时失效。

举报的人不需要找到其他受害者，只需要让那把被反复使用的钥匙作废。顺带一提，两枚样本和加密包在吊销确认后已经销毁——留下来的证据是哈希、证书公开文件和吊销检索结果，足够任何人复核这条链路：

- CRL 检索：`http://crl.globalsign.com/gsgccr45evcodesignca2020.crl`（查序列号 `046CD9B4FAD9F7C7101A6578`）
- 按主体检索：`https://crt.sh/?q=NewWnight`[^crtsh]

> 删掉两个文件，救的是一台机器；吊销一张证书，废掉的是一整套工具链。

## 十、如果只记三件事

这次经历里，最值钱的不是"哪个文件有毒"，而是几个判断方法。压缩成三条：

1. **签名有效 ≠ 文件安全，甚至 ≠ 证书未被吊销。** 签名只证明"谁签的、有没有被改"；而 Windows 的默认校验对吊销是软失败——证书进了吊销列表，它照样告诉你"有效"。签名是"必要不充分"的信任依据，不是免检金牌。

2. **看到 `svchost` 先别下结论，看同一时刻谁在请求。** 大量网络日志会把行为归到 `svchost`，因为 DNS 解析是它统一代做的。真正的发起者，往往藏在同一时间窗口的另一条日志里。

3. **告警形态相似，性质可能相反。** 同一台机器上，有签名的 DLL 是真木马，没签名的开源插件反而是误报，聊天软件报警只是浏览器在预解析链接。判断时看：文件是否与官方清单/上游源码对得上、操作进程是谁、代码是在"正常的干这件事"还是"用木马的标准手法干这件事"。

那天上午的处置是一场虚惊：两个文件被隔离，清理干净，Steam 覆盖重装，安装包签名核验为 Valve 官方。但故事没有停在虚惊——第二天，那张空壳公司的 EV 证书进了吊销列表，在线校验返回 `Revoked`。

删掉两个文件，救的是一台机器；吊销一张证书，废掉的是一整套工具链。攻击者不需要骗过安全机制，只需要骗过"扫一眼就点允许"的人；而举报的人，也不需要找到每一个受害者——只需要让那把被反复使用的钥匙作废。这大概是这次事件里，比"少一个字母 v"更值得记住的事。

[^dnscache]: Dnscache（DNS Client）是 Windows 的 DNS 客户端服务，通常运行在 `svchost.exe` 进程内，替所有程序统一发起域名解析，所以网络日志里常把行为归因到 `svchost.exe`。

[^dllorder]: DLL 搜索顺序劫持：程序加载 DLL 时按固定顺序查找目录，把同名恶意 DLL 放在优先位置（通常是程序自身目录）即可被加载，不需要修改原程序。

[^ev]: EV 代码签名证书（Extended Validation）：需要企业实名与对公验证、费用高于普通证书的签名证书，能获得更高的系统信任，但"获得信任"不等于"值得信任"。

[^crl]: CRL（Certificate Revocation List，证书吊销列表）：CA 定期发布的"作废证书名单"，客户端启用吊销检查时，证书出现在名单里就应拒绝信任。

[^crtsh]: crt.sh 是公开的证书透明度检索服务。注意按序列号检索的 `?serial=` 参数形式实测返回 404，应按主体名检索。
